# Introducing Obscuretone Test ROM: A Game Boy Diagnostic That Explains Itself

Emulator testing has an awkward blind spot. Unit tests can prove that a Python
function returned the expected value, but they cannot prove that a complete
emulated machine fetched an instruction from a cartridge, routed its memory
access through the bus, advanced the timer and video hardware, and reported the
right result.

That is why I built **Obscuretone Test ROM**, or **OTR**: a self-checking DMG
Game Boy diagnostic that runs as an actual cartridge image, shows its progress
on the Game Boy display, streams structured events over the serial port, and
halts at the first failure.

OTR began as a way to test PyGameBoy, but it is deliberately maintained as its
own project. It has its own build, tests, release artifacts, result protocol,
and identity. It is not a wrapper around Blargg, Mooneye, or another existing
compatibility suite. Those projects remain invaluable; OTR approaches the
problem from a different direction.

## Testing the machine, not just the implementation

An emulator can pass a test that calls an opcode method directly while still
failing to run the same opcode from a ROM. Instruction decoding might be wrong.
The program counter might advance incorrectly. A memory write might bypass an
MBC or I/O side effect. An interrupt might arrive at the wrong point.

OTR goes through the integrated path. The emulator loads a cartridge, reads its
header, selects a memory controller, fetches instructions, and advances the
connected timer, serial, PPU, and APU components. The core ROM executes every
runnable legal base opcode and all 256 CB-prefixed opcodes. STOP has a dedicated
probe, as do the eleven undefined opcode encodings, because neither category can
safely return to an ordinary sequential test runner.

The suite also checks CPU-visible behavior across:

- registers, flags, loads, arithmetic, stack operations, and control flow;
- interrupts, timer overflow, divider behavior, and serial transfers;
- WRAM, echo RAM, HRAM, cartridge RAM, and unusable memory;
- joypad selection, OAM DMA, PPU state, and rendered output;
- APU power, register behavior, all four channels, and produced audio;
- MBC0, MBC1, MBC2, MBC3 with RTC registers, and MBC5 with its ninth ROM-bank
  bit.

One cartridge header cannot identify itself as five different controller
types, so controller behavior lives in separate generated ROMs. MBC5's ninth
bank bit requires a large physical address range, which makes that image eight
megabytes. It is almost entirely zero-filled and compresses extremely well.

## A ROM that says what it is doing

Many test ROMs appear frozen while they work. If something goes wrong, it can be
hard to tell whether the emulator crashed, the test is slow, or the result
reporter itself failed.

OTR includes a tiny tile font and live status console. The first background row
shows the active group:

```text
20 CB OPCODES
```

At the same time, the ROM emits line-oriented ASCII over the Game Boy serial
port:

```text
OTR/1 01 CPU LOAD MATRIX
OTR/1 20 CB OPCODES
OTR/1 35 APU
OTR/1 PASS
```

The `OTR/1` prefix is a versioned protocol boundary rather than decorative
text. A headless runner can parse it without screen capture or emulator-specific
hooks.

On failure, OTR records the current group and case, prints the diagnostic before
the terminal event, disables interrupts, and executes HALT:

```text
OTR/1 ERROR
AT 20:7C
OTR/1 FAIL
```

The core ROM also exposes an `OTR1` mailbox in cartridge RAM. It contains the
running, pass, or fail state; the current group and case; and a NUL-terminated
result message. Serial is the most human-readable output, while the mailbox is a
simple fallback for automated runners.

## A build system that audits itself

OTR is generated by a dependency-free Python program. It does not require an
external assembler, which keeps builds reproducible across development machines
and CI environments.

The generator is more than a byte emitter. Whenever it emits an instruction, it
records that encoding in a coverage ledger. Generation fails if the core suite
does not account for every legal base opcode or every CB opcode. It produces a
JSON manifest containing the protocol version, exact coverage lists, output
sizes, and SHA-256 hashes for the core, controller, and probe ROMs.

That manifest defines a clean relationship between OTR and an emulator that
vendors it. OTR owns the source and generation tests. PyGameBoy keeps release
artifacts and verifies every vendored byte against the upstream hashes before
running them through its complete machine graph.

The source of truth therefore stays in its own repository instead of becoming
an emulator-specific subdirectory.

## What “every opcode” does—and does not—mean

OTR executes every legal encoding, but no finite ROM can test every possible
Game Boy state. Two eight-bit operands already create 65,536 input pairs before
carry, flags, memory timing, interrupts, and peripheral state enter the picture.
The full machine state is vastly larger.

The suite uses independent result and flag oracles with deliberately chosen
boundary vectors. This catches encoding, register-selection, flag, memory, and
integration errors without pretending to exhaust an effectively unbounded state
space.

There is another important boundary: cartridge software cannot directly inspect
the host framebuffer or speaker buffer. OTR verifies the CPU-visible side of the
PPU and APU, while the emulator's host harness checks the rendered pixels and
produced audio. The same division applies to STOP and undefined-opcode behavior,
which need observation from outside the running program.

Accuracy comes from combining these layers, not from asking one test mechanism
to observe things it cannot see.

## Building OTR

Python 3.10 or newer is the only build requirement:

```bash
git clone https://github.com/Obscuretone/obscuretone-test-rom.git
cd obscuretone-test-rom
python generate.py --output dist
python generate.py --output dist --check
```

The output includes:

- `otr.gb`, the 32 KiB core diagnostic;
- controller-specific MBC ROMs;
- STOP and undefined-opcode probes;
- `manifest.json`, containing hashes and the complete coverage ledger.

Generated ROMs intentionally leave the Nintendo logo area blank. They are meant
for emulators that skip the original boot ROM. OTR does not redistribute
Nintendo-owned logo data, so an original DMG running its boot ROM will reject
the cartridge during the hardware logo check.

## Why build another test ROM?

Because readable failures change how emulator work feels.

Instead of wondering whether a black window means “still running,” OTR shows the
active subsystem. Instead of a generic timeout, it reports a stable group and
case. Instead of trusting that a collection of opcode bytes happens to be
complete, the generator refuses to build an incomplete ledger. Instead of
binding the diagnostic to one emulator's source tree, the manifest creates a
small, verifiable contract between independent projects.

OTR will not replace focused timing suites, hardware measurements, or carefully
written unit tests. It gives them a useful companion: one cartridge-shaped
program that travels through the whole emulated machine and explains what it is
doing along the way.

That makes failures easier to reproduce, easier to understand, and—most
importantly—harder to ignore.
